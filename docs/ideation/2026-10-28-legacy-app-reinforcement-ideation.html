The Sieś Files · discovery brief

Reinforce the app without losing the behavior you inherited

Date: 2026-10-28Topic: legacy-app-reinforcementScope: current codebase

Focus: security, reliability, code quality, legal readiness, bug fixes and missing capabilities—with regression avoidance as a constraint on every direction.

Best starting direction: a reproducible baseline for the exact inherited workspace. It makes each later hardening change easier to evaluate. Zero regressions cannot be guaranteed; reproducible evidence, small changes and demonstrated recovery reduce the risk.

46 original ideas → 22 consolidated candidates + 4 combinations → 7 ranked directions. All 26 candidates were challenged; 19 had sound bases and 7 were weak. Strong overlapping ideas were merged or narrowed rather than turned into parallel projects.

Codebase Context

This application already has substantial foundations: domain services, separate public/player/Storyteller projections, PostgreSQL-backed transactional commands, expected-version checks, persisted idempotency receipts, checkpoint infrastructure, authorization boundaries and CI. Reinforcement should extend these strengths.

The historical audit explicitly targets main@9099836. Some missing features it describes now exist. Its rows need reconciliation with current behavior before becoming a new defect backlog. The workspace also contains substantial uncommitted UI, package and test work; assessing only committed HEAD would omit part of the inherited application.

Source inspection identified concrete leads: the event-stream client does not handle the server’s initial version message; replay verifies a narrower state set than whole-game recovery; receipt decoding remains optional; a role-dependent browser test assumes a randomized setup includes particular roles. CI and test source were inspected, but no passing runtime baseline was established.

Ownership, content-permission, data-retention and deployed-operation evidence remains incomplete. Missing documents are evidence gaps, not findings of infringement or noncompliance. Actual hosting topology, proxy behavior, backup practices, jurisdiction and intended distribution remain unverified.

Evidence limits: no application changes, test execution, vulnerability scan, production inspection or legal determination. No secrets were read. External research was unavailable because a dedicated web-search tool was absent. Confidence below means confidence that a direction deserves exploration, not a measured assurance level. The two-frame generator shared its verification budget, so source-reading depth varied; a separate verifier challenged every consolidated candidate and spot-checked live source.

Topic Axes

  1. Access and abuse boundaries: who can observe or act, including revocation and proxy trust.
  2. State recovery and live delivery: whether clients catch up and interrupted games remain playable.
  3. Regression confidence and release control: reproducibility, attribution and evidence for the exact changed workspace.
  4. Rules correctness and maintainable contracts: valid actions and durable results across retries and releases.
  5. Ownership, participant data and operational stewardship: provenance, information survival and successor responsibilities.

All five axes have surviving directions. Ranking weighs evidence strength, expected value, leverage, feasibility, burden and overlap. A demonstrated actively exploited defect or failing production recovery would change the immediate priority; neither was established here.

1. Establish a reproducible inherited baseline

Confidence: 95%Complexity: Medium
Description
Make the actual inherited workspace—including relevant untracked UI files and dependency changes—a reproducible comparison point. Preserve known failures and deterministic synthetic game scenarios, so each small reinforcement can be compared against the same starting conditions. Serious bugs should leave a minimal repeatable specimen rather than a timing anecdote. This is an evidence habit, not a new snapshot or incident-recording platform.
Axis
Regression confidence and release control.
Basis
reasoned: the current dirty tree contains changed package manifests, routes, presentation components and browser tests. tests/e2e/e2e-04-succession.spec.ts:9–26 commits randomized setup before assuming a CHEF/MONK assignment. playwright.config.ts:42–48 uses a development server, while .github/workflows/ci.yml:61–65 builds production afterward. These are different test conditions; a single red or green run cannot establish attribution or production behavior.
Rationale
Every security patch, bug fix and refactor becomes easier to judge when existing failures and relevant behavior are reproducible. Exact workspace attribution protects the ongoing UI work and avoids labeling inherited failures as new regressions. Review old audit claims against these observations instead of assuming the audit still describes the code.
Downsides
Some initial effort produces confidence rather than features. Captures need deliberate exclusion of credentials and generated artifacts. Deterministic scenarios do not reproduce every race, and existing CI remains valuable rather than being replaced.

2. Reconcile state before calling the client live

Confidence: 95%Complexity: Medium
Description
Separate a connected transport from a screen that has caught up with authoritative game state. Explore bounded reconciliation at initial connection, reconnect and foreground return, with a visible catching-up state where appropriate. Notifications can accelerate freshness; correctness should not rely on receiving every notification. Existing server-side version checks remain the final mutation guard.
Axis
State recovery and live delivery.
Basis
direct: src/app/api/v1/games/[gameId]/events/stream/route.ts:63–64 sends send("hello", game.version, game.eventSequence). src/components/useGameEventStream.ts:66–68 registers open, error and invalidate listeners, without a hello reconciliation handler. The test comment at tests/e2e/e2e-07-map-unlock.spec.ts:57–59 warns that a scan before the connection opens “is missed forever.”
Rationale
This is a bounded, source-supported reliability direction that can reduce stale decisions and timing-dependent tests without replacing the in-memory broker. The important property is agreement with database truth after disruption, not merely a green connection label.
Downsides
Extra fetches and temporary waiting states affect latency. Overlapping responses can themselves introduce stale-state races. Convergence must be conditional on server reachability; browser suspension and network loss rule out an unconditional freshness guarantee.

3. Prove recovery by continuing a restored game

Confidence: 95%Complexity: High
Description
Treat recoverability as evidence that a restored synthetic game can complete its next legal action in a fresh process, ideally with a second operator. Describe separately what checks prove about checkpoint integrity, players, votes, pending decisions, phase and scenario state. A loaded dump or a replay success flag should not imply a stronger continuation guarantee than was actually exercised.
Axis
State recovery and live delivery.
Basis
direct: src/modules/recovery/recovery.service.ts:361–415 checks event continuity and player alive/ghost-vote state, rather than reconstructing the entire game. scripts/backup-restore.sh:19–23 counts restored tables before announcing verification. tests/e2e/e2e-08-restart-recovery.spec.ts:11–13,42–58 checks mid-vote consistency/replay but does not itself restart a server; the inspected CI has no physical-restart step.
Rationale
Durability is one of the app’s strongest existing foundations, making playable continuation a high-value next assurance. Honest coverage also prevents a new owner from trusting a narrow diagnostic as a complete disaster-recovery promise. A cold operator exercise reveals missing assets, access and runbook knowledge that database checks cannot.
Downsides
This is the highest-burden direction: isolated restore environments and representative unfinished game states require care. Full event-sourced reconstruction may not be necessary or economical. Deployment topology, backup storage and recovery targets remain facts to establish, not assumptions this assessment settled.

4. Challenge access and secrecy through the real boundary

Confidence: 90%Complexity: Medium
Description
Evaluate selected hostile-viewer journeys: another game’s participant, an expired or revoked session, a former player with an open stream, and an anonymous claimant. Use synthetic secret markers and paired game states to challenge audience isolation across projections, errors, protected assets and realtime metadata. Include the deployed proxy’s authority over host/address headers and the configuration under which abuse controls actually run.
Axis
Access and abuse boundaries.
Basis
reasoned: scoped projections and protected routes already exist at src/modules/projections/projections.ts:30–95 and src/app/api/v1/games/[gameId]/map/layers/[layerId]/route.ts:18–45. The stream resolves membership on entry at src/app/api/v1/games/[gameId]/events/stream/route.ts:35. Origin/IP decisions depend on forwarded values in src/lib/auth/http.ts and src/lib/rate-limit.ts:28–31. Entry authorization and source configuration do not establish behavior after revocation or through the production proxy.
Rationale
This builds on existing security design while checking transitions and secondary disclosure paths. It is more informative than merely counting authenticated endpoints. A current dependency/advisory inventory can complement the behavioral evidence; dependency metadata alone does not establish exploitability.
Downsides
The real deployment and permitted audience distinctions must be understood. Paired-state tests need narrowly defined secrets and legitimate reveals; not every version change must be invisible. Marker absence cannot prove all possible leaks. No exploitable vulnerability was established by this source review.

5. Make durable command outcomes safe across retries and releases

Confidence: 90%Complexity: Medium
Description
Extend the existing command identity and receipt machinery to settle a consequential action after response loss, using actor-scoped access and validated results. Treat durable JSON as a compatibility boundary across releases, starting with a representative meaningful command outcome. Explore whether a candidate and its rollback can interpret already-committed outcomes without repeating their effects.
Axis
Rules correctness and maintainable contracts.
Basis
direct: src/lib/command.ts:126–158 makes resultSchema optional and retains (existing.resultJson ?? null) as T for unvalidated results. src/modules/scenario/scenario.service.ts:93–99 returns structured scan data without supplying a result codec. The verifier also confirmed fresh client command IDs per attempt and an existing Storyteller-only status lookup; command status is not a wholly missing subsystem.
Rationale
Runtime result contracts improve maintainability at a real seam rather than triggering broad refactors. Existing transactional idempotency is valuable, but a person who lost a response still needs to learn what happened. Persisted records outlive the code that wrote them, so fresh-database tests alone cannot establish compatibility.
Downsides
Historical result formats and access rules need explicit treatment. An invalid old receipt must not cause a committed mutation to run again. Not all database migrations are reversible, and a full multi-build compatibility platform would be excessive as the first intervention.

6. Establish provenance for the actual playable release

Confidence: 90%Complexity: Medium
Description
Build a compact release-linked account of code ownership and contributor rights, game-content sources, names/prose/artwork, asset derivatives, fonts, and the dependencies actually distributed. Record evidence of permitted use, required notices and unresolved questions against the intended private/public/commercial context. Keep permission to distribute independent from permission to reveal an asset during play.
Axis
Ownership, participant data and operational stewardship.
Basis
direct: the-sies-files-docs/00_README.md:35 names “Blood on the Clocktower: Trouble Brewing” as the reskinned ruleset. scripts/build-map-assets.mjs:4–7 traces canonical artwork into public/protected derivatives. src/content/manifest.ts:10–11 states productionReady: false pending production art and approved prose/names. Inspected tracked paths did not establish first-party license/notice documents or permission records.
Rationale
Inheritance creates uncertainty about who supplied what and under which terms. Exact release provenance turns “is this legally ready?” into bounded evidence questions for the owner and, where needed, an appropriate legal reviewer. Lockfile license strings and transformed artwork do not answer those questions by themselves.
Downsides
Repository evidence may not contain agreements held elsewhere. Applicable obligations depend on actual use and distribution. This direction does not presume infringement, mandate wholesale content replacement or certify legal clearance.

7. Decide what survives after a participant or game leaves

Confidence: 90%Complexity: Medium
Description
Make participant-data survival understandable across roster records, sessions, events, command results, snapshots, exports, client caches and backups. Establish the purpose, audience and lifetime of retained data, including what a restore could reintroduce. Consider participant-facing explanations and removal handling alongside the operator’s need to investigate or resume games, before choosing destructive retention changes.
Axis
Ownership, participant data and operational stewardship.
Basis
direct: src/modules/game-session/game-session.service.ts:239–253 deletes a roster row and appends PLAYER_REMOVED with displayName. prisma/schema.prisma:163,182,414 restricts deletion of retained history, while :167–170,185,417–421 provides event JSON, receipt results and snapshots. The historical security spec describes a conditional separate retention procedure; inspections did not establish implemented retention durations or cleanup schedules.
Rationale
Removing a player from the roster is not equivalent to removing identifying details from history. A clear data-lifecycle decision connects privacy, reliability, incident handling and ownership handoff without silently undermining the audit trail or restore behavior.
Downsides
Retention and recovery goals can conflict. Pseudonymous identifiers are not automatically anonymous, and backup expiry is different from immediate deletion. Actual legal obligations depend on jurisdiction and processing context; neither was established here.
